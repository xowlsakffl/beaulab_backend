# 로컬 개발 데이터 사용 안내

[FrontendDevelopmentSeeder](../database/seeders/FrontendDevelopmentSeeder.php)는 새 프론트 개발자 PC에서 로그인·권한·채팅·이벤트 상태를 확인하기 위한 소규모 합성 데이터다. 운영 DB 덤프나 실제 고객 자료를 사용하지 않는다.

## 실행 정책

- 기본 `DatabaseSeeder`는 권한·직원·카테고리·병의원 특징만 준비합니다. 전체 데모는 `DEVELOPMENT_SEED_ENABLED=true`일 때만 함께 실행합니다.
- 개별 개발 샘플 시더와 전체 데모에는 `DEVELOPMENT_SEED_ENABLED=true`, `DEVELOPMENT_SEED_DATABASE=<실제 로컬 DB 이름>`이 필요합니다. local/testing, 로컬 MySQL, 공개·비공개 local 미디어 디스크, SMS/PUSH 비활성화를 함께 검사합니다.
- 전체 데모는 기존 업무 데이터가 있으면 쓰기 전에 거절합니다. 동시 실행 잠금과 DB 트랜잭션을 사용하며, 실패한 파일 쓰기는 미디어 staging 정리 대상입니다. 기존 DB에서 초기화 명령으로 재실행 조건을 맞추지 않습니다.
- 카테고리·병의원 특징은 기존 이름·순서·상태·메뉴 표시를 초기화하거나 정의에서 빠진 항목을 삭제하지 않습니다. 신규 DB의 분류 준비는 업무별 분리와 통합 조회 연결을 함께 만들며, 전환 대응표가 존재하면 의료 분류를 재복제하지 않습니다. 기존 DB 전환은 전체 Seeder가 아닌 승인된 전환 절차를 사용합니다. 후기·이벤트·평가·토크 샘플 시더는 기본 분류를 다시 동기화하지 않습니다.
- 초기 직원과 역할별 테스트 직원은 없는 계정만 생성합니다. 기존 계정의 비밀번호·상태·권한은 유지합니다. `AuthorizationSeeder`의 역할별 권한 동기화는 별개이므로 실행 전 변경 범위를 확인합니다.
- `FrontendDevelopmentSeeder`는 아래의 별도 신규 환경 정책을 사용하며 DEVELOPMENT_SEED 설정은 필요하지 않습니다.
- Factory의 기본 관계는 Laravel 관계 Factory로 생성합니다. 기존 회원·병의원·이벤트를 재사용하려면 ID 또는 상태 메서드로 명시합니다. 속성을 지정하기 전에 임의 의료진·이미지를 먼저 생성하지 않으며 프로세스 전역 ID 캐시도 사용하지 않습니다.
- 동영상 URL은 재생 보장이 없는 임의 테스트 URL을 유지합니다. 썸네일·목록용 데이터이며 실제 영상 재생 검증용이 아닙니다.

## 생성 방법

[로컬 설치 절차](local-setup.md)를 먼저 완료한다. `.env.frontend.example`을 기준으로 전용 DB를 구성하고, 개인별 개발 비밀번호와 최초 실행 활성화 값을 지정한다.

```bash
php artisan db:seed --class=FrontendDevelopmentSeeder
```

실행 조건:

- APP_ENV=local, FRONTEND_SEED_ENABLED=true
- FRONTEND_SEED_PASSWORD 최소 12자
- 로컬 MySQL 연결, 실제 DB 이름이 `beaulab_frontend_`로 시작
- 마이그레이션 이력·초기 예약 잠금 행·변경되지 않은 배너 기본 노출위치 5행을 제외한 테이블에 데이터가 없음
- 공개·비공개 미디어 디스크가 모두 local
- SMS_ENABLED=false, PUSH_ENABLED=false

재실행은 거절한다. 기존 계정 비밀번호·상태·사용자가 만든 데이터를 덮어쓰지 않는다. 기본 DatabaseSeeder 또는 DemoSeeder와 함께 실행하지 않는다. 생성 중 DB 실패는 트랜잭션으로 되돌리지만 생성된 로컬 이미지 파일은 남을 수 있으므로, 실패 시 로그와 파일 경로를 확인한 뒤 담당자가 정리한다.

## 로그인 계정

비밀번호는 모두 **이 PC의 `.env`에서 본인이 지정한 FRONTEND_SEED_PASSWORD**다. 고정된 공용 비밀번호를 문서나 저장소에 두지 않는다. 같은 비밀번호를 사용하는 이 데이터 세트는 개인 로컬 전용이며 공용 개발 서버·운영에 배포하지 않는다.

| 계정 유형      | 로그인 입력값             | 확인할 상황                             |
| -------------- | ------------------------- | --------------------------------------- |
| 직원 관리자    | `frontend_admin`          | 직원 화면·내부 API 문서 접근, 관리 기능 |
| 권한 없는 직원 | `frontend_restricted`     | 보호된 업무 API·페이지의 접근 거절      |
| 일반 사용자 A  | `alice@frontend.test`     | 기존 채팅·메시지, 사용자 API            |
| 일반 사용자 B  | `bob@frontend.test`       | 상대방 메시지·채팅 동기화               |
| 빈 사용자      | `empty@frontend.test`     | 채팅·알림 등이 없는 초기 상태           |
| 정지 사용자    | `suspended@frontend.test` | 로그인 제한·오류 안내                   |
| 병의원 alpha     | `frontend_hospital_alpha` | 본인 병의원 범위                          |
| 병의원 beta      | `frontend_hospital_beta`  | 다른 병의원 리소스 접근 제한 비교         |

직원·병의원은 **아이디(nickname)**, 일반 사용자는 **이메일(email)**로 로그인한다. 직원 이메일은 admin@frontend.test·restricted@frontend.test, 병의원 이메일은 hospital-alpha@frontend.test·hospital-beta@frontend.test로 별도 저장되며 웹 로그인 입력값과 다르다.

관리자 계정은 로컬 API 문서 열람을 위해 super_admin 역할을 가진다. 실제 업무 계정 권한 정책의 예시가 아니다. restricted 계정에는 업무 권한을 주지 않는다. 로그인과 업무 API 접근 허용은 구분해서 확인한다.

## 제공하는 데이터

| 데이터             | 수량        | 내용                                                           |
| ------------------ | ----------- | -------------------------------------------------------------- |
| 권한·역할          | 기존 정의   | AuthorizationSeeder 기준                                       |
| 카테고리·병의원 특징 | 기존 기본값 | CategorySeeder·HospitalFeatureSeeder 기준                      |
| 직원               | 2명         | 관리자·권한 없음                                               |
| 일반 사용자        | 4명         | 정상 3명·정지 1명                                              |
| 병의원·병의원 계정     | 각각 2개    | 승인·정상 병의원과 병의원별 owner 계정                             |
| 이벤트             | 4개         | 병의원별 기간 제한 없는 이벤트 1개·종료된 이벤트 1개             |
| 이미지             | 8개         | 병의원별 로고·갤러리, 이벤트 썸네일. 저장소의 테스트 이미지 사용 |
| 채팅               | 1방·2메시지 | alice와 bob의 텍스트 대화, 실제 발송·푸시 없음                 |
| 지갑               | 2개         | 잔액 0, 거래 원장 없음                                         |

생성 로그에 실제 리소스 ID와 로그인 입력값이 출력된다. 자동 증가 ID를 프론트 코드에 고정하지 않는다. 계정 이메일·데이터 이름으로 조회한 ID를 사용한다. 상세 필드의 일부는 Faker로 만들어지므로 PC마다 완전히 동일한 값이 생성되지는 않는다.

기간 제한 없는 이벤트는 시일이 지나도 테스트에 사용할 수 있다. 종료 이벤트는 생성 시점 기준 이미 끝난 기간을 가진다. 지갑 잔액은 원장 없이 임의로 늘리지 않는다. 유료 신청·충전·환불 테스트가 필요하면 별도 업무 흐름으로 데이터를 준비한다.

## 확인 순서

1. user-web에서 alice 로그인, 프로필 확인 후 로그아웃한다.
2. 사용자 토큰 API 또는 구현 중인 RN에서 alice·bob의 채팅 목록·메시지를 확인한다.
3. empty 계정은 빈 목록, suspended 계정은 로그인 거절을 확인한다.
4. staff-web 관리자 로그인 후 병의원 2개·이벤트 4개와 샘플 이미지를 확인한다.
5. hospital-web에서 각 병의원 계정 로그인을 확인한다. 소유권 테스트는 실제 구현된 병의원 API로 진행한다.
6. 권한 없는 직원으로 보호 API 접근이 거절되는지 확인한다.

현재 user-web에 채팅 UI가 없으므로 웹 화면에서 모든 데이터가 보일 것이라고 가정하지 않는다. 사용자용 병의원·이벤트 전체 조회 API도 준비 완료 상태가 아니다. 데이터 존재 여부와 화면·API 구현 완료는 별개다.

## 제공하지 않는 것

- 실결제·실환불·실 SMS·실 푸시, 외부 메일 전송
- 공지·후기·평가·토크·광고 등 모든 도메인의 대량 데이터
- 입점·사업자 서류, 실제 개인정보·계좌, 실서비스용 계정
- 업무 이력·알림 발송을 실제로 거친 채팅 데이터

이벤트·병의원 기본 데이터는 UI 연동용 모델 상태다. 등록 API의 전체 검증·감사 이력까지 재현한 데이터는 아니다. 다른 업무의 테스트는 기존 개별 Seeder의 생성·삭제·갱신 범위를 확인한 뒤 별도 빈 DB에서 준비한다.

## 코드 업데이트와 데이터 보존

### 병의원 챗봇 상담 화면 샘플

`php artisan db:seed --class=HospitalChatBotConsultationSeeder`는 기존 활성 직원·승인된 병의원 계정을 이용해 대기 3건, 상담 중 4건, 종료 12건, 취소 3건을 추가합니다. 계정·권한·운영시간은 변경하지 않습니다. 로컬 또는 테스트 환경의 로컬 DB에서만 실행할 수 있습니다.

- 메시지 없는 상담, 다른 직원 담당 상담, 245개 메시지의 긴 상담, 여러 줄 답변과 상태 이력이 포함됩니다.
- 기존 활성 상담은 유지하며, 활성 상담이 없는 병의원 7곳이 필요합니다. 부족하면 추가 전체를 취소합니다.
- `source_application=local-chatbot-scenarios-v1`로 구분합니다. 재실행해도 기존 샘플의 내용·상태·시각을 덮어쓰거나 중복 생성하지 않습니다.
- 대기 샘플에도 기본 30분 자동 만료 정책이 적용됩니다. Scheduler가 실행 중이면 이후 취소로 이동할 수 있습니다.
- 실시간 발행 대기 표식을 끈 상태로 메시지를 저장하며 외부 알림·메일은 발송하지 않습니다.

## 기존 데이터 보존

### 신고 화면 샘플

`php artisan db:seed --class=ReportedContentDevelopmentSeeder`는 기존 로컬 DB에 신고 화면용 합성 데이터를 추가합니다. 위의 개발 데이터 실행 제한을 모두 적용하며, 활성 직원·승인 병의원·활성 토크/평가 카테고리·분류가 연결된 성형/쁘띠 후기·`public/test.png`가 필요합니다.

- 성형/쁘띠 후기와 댓글, 토크와 댓글, 평가에 신고접수·자동미노출·관리자미노출·정상노출을 생성합니다. 채팅에는 미처리·경고·무시 샘플을 추가합니다. 신규 환경 기준 신고 대상 31개, 신고 115건입니다.
- 샘플 회원은 `reported-content-*@seed.test`, 게시물은 `[개발용 신고]` 접두사로 구분합니다. 연락 가능한 전화번호나 로그인용 공용 비밀번호를 만들지 않습니다.
- 같은 샘플이 있으면 건너뜁니다. 기존 샘플의 상태·내용·신고 시각을 초기화하거나 삭제된 샘플을 복원하지 않습니다. 기본 DatabaseSeeder에 자동 연결하지 않습니다.
- DB 잠금과 트랜잭션으로 동시 실행·부분 생성을 막습니다. 기존 게시물·회원·권한은 수정하지 않으며, 새 샘플에 따른 병의원 평가 집계와 샘플 작성자 경고 수만 반영합니다.
- 모델 이벤트와 채팅 실시간 발행을 사용하지 않습니다. 실제 사용자 신고 API·SMS·푸시·큐 발송을 재현하는 통합 검증 데이터가 아닙니다. 이미지 저장 실패 후에는 미디어 staging 정리 정책을 따릅니다.

### 배너/팝업 샘플

`php artisan db:seed --class=BannerExposureDevelopmentSeeder`는 로컬 DB·이미지 저장소에 메인 팝업/세로배너/가로배너·상담메모장·검색창 샘플을 추가합니다. 기존 승인 병의원, 등록 권한이 있는 직원, 활성 기획전 카테고리가 필요합니다.

- 직접 등록 29건(기획전/페이지), 광고 최대 17건, 연결 이벤트 5건과 로컬 샘플 이미지를 생성합니다. 노출중·진행예정·비공개·기간종료를 포함합니다.
- 메인 팝업은 직접 등록 6개 이후 광고 3개가 들어오는 9/6 상황입니다. 기존 광고가 슬롯을 점유하면 광고는 남은 자리만 추가합니다.
- `[노출설정 샘플]` 배너명과 `[샘플]` 이벤트명으로 구분합니다. 같은 샘플의 상태·기간·클릭수는 재실행으로 초기화하지 않으며, 날짜가 지나면 자연스럽게 종료됩니다. 식별용 샘플명은 변경하지 않습니다.
- 광고 승인 모델 상태만 생성하고 충전금 차감·외부 알림·승인 업무 이력은 실행하지 않습니다. 결제/승인 통합 검증 데이터로 사용하지 않습니다. 전체 DatabaseSeeder에는 자동 연결하지 않습니다.

- 평소 재시작에는 migrate나 seed가 필요하지 않다. 서비스를 시작하고 API만 실행한다.
- 코드를 갱신할 때 composer.lock 변경과 마이그레이션 변경을 확인한다. 기존 생성 migration 수정은 이미 적용된 DB에 자동 반영되지 않는다.
- 데이터 세트를 새로 만들 필요가 있으면 기존 DB를 남겨 두고 새 `beaulab_frontend_<이름>` DB와 해당 사용자 권한을 준비한다. 환경 파일의 연결값을 바꾼 뒤 빈 DB에만 migrate·seed한다.
- 자동 초기화·전체 Seeder 재실행·Redis FLUSHALL로 문제를 해결하지 않는다. 업무 중 만든 데이터 삭제가 필요한 경우 대상과 보존 여부를 먼저 확인한다.
- 계정을 직접 수정한 후 이 문서의 예시와 달라졌다면 현재 DB 상태가 우선한다. Seeder를 재실행해 원복하지 않는다.
