# 도메인 규칙

공통화하면 안 되는 상태 의미와, 변경할 때 놓치기 쉬운 계약을 모았습니다.
전체 상태·필드 사전은 복제하지 않습니다. 저장값·라벨은 Model, 입력 허용값은 Request, 전이와 인가는 Action·Policy가 기준입니다.

## 상태를 분리해서 볼 것

| 대상               | 구분해야 할 상태                                   |
| ------------------ | -------------------------------------------------- |
| 병의원             | 검수 상태, 운영 노출 상태, 연결 계정의 로그인 상태 |
| 의료진·뷰티·전문가 | 각 도메인의 검수 상태와 운영 상태                  |
| 이벤트             | 병의원 설정, 관리자 강제 상태, 검수 상태             |
| 영상               | 병의원 상태, 관리자 처리 상태와 신고 상태            |
| 병의원 평가        | 영수증 검수, 게시 처리, 공개 상태                  |
| 충전금             | 업무 유형별 처리 상태와 실제 원장 생성 여부        |

병의원 운영중지는 미노출이지 로그인 차단이 아닙니다. 계정 정지는 AccountHospital에서 별도로 다룹니다.
신규 병의원의 검수값은 `NOT_APPLIED`이며 화면에는 미신청으로 표시합니다. Beauty/BeautyExpert에 병의원과 동일한 중간 검수 상태가 모두 있는 것은 아닙니다.

일반 수정과 상태 변경 권한은 분리합니다. 권한이 없는 화면은 현재 상태만 보여주더라도 서버는 별도로 인가해야 합니다.
카테고리·공지처럼 단순 공개 상태인 경우에도 해당 도메인의 상태 변경 규칙을 확인합니다.

## 병의원 운영중지 요청

[Hospital Actions](../app/Domains/Hospital/Actions)에서 직접 처리와 신청을 구분합니다.

- 직접 상태 변경 권한이 없더라도 별도 신청 권한이 있는 직원은 사유를 포함한 운영중지 신청을 만들 수 있습니다. 일반 수정 권한만으로 신청 권한을 대신하지 않습니다. 신청 대기는 아직 운영 상태 변경이 아닙니다.
- 처리 권한이 있는 활성 직원에게 알림을 생성합니다. 알림함 데이터가 있다는 것이 별도 결재 화면까지 구현됐다는 뜻은 아닙니다.
- 승인 시 상태 변경, 반려 시 사유 기록을 처리합니다. 본인의 신청을 직접 승인·반려하지 않습니다.
- 권한자가 직접 상태를 변경하는 경로는 기존 대기 신청을 함께 정리합니다.
- 병의원 상태·요청 상태·이력을 하나의 업무 변경으로 다룹니다.

## 카테고리

[Category 도메인](../app/Domains/Common/Category)의 domain, group_code, usage는 서로 다른 개념입니다.

- domain은 분류 체계, group_code는 성형/시술/기획전 같은 구분, usage는 화면별 사용 가능 범위입니다.
- 그룹은 트리의 가짜 부모 노드가 아닙니다. 실제 계층은 parent_id로 연결합니다.
- 이벤트는 활성 자식이 없는 선택 가능 노드를 사용합니다. 자식 없는 대·중카테고리도 가능하며 깊이 3만 강제하지 않습니다.
- 성형·시술 이벤트는 같은 그룹에서 최대 3개와 그중 대표 1개를 선택합니다.
- 기획전은 1개만 선택하고 그것이 대표입니다. 다른 그룹과 섞지 않습니다.
- 기획전은 리얼모델·수능이벤트·제모·첫만남 이벤트를 별도 코드로 갖습니다. 시술 분류의 제모와 같은 데이터로 취급하지 않습니다.
- 병의원·의료진 진료 과목, 영상, 후기에는 각각 다른 usage와 선택 규칙이 있습니다. 이벤트의 leaf/개수 규칙을 전부 공용 검증으로 강제하지 않습니다.

트리 최초 조회는 usage, 하위 조회는 parent_id, 검색은 usage와 q에 따른 범위로 동작합니다.
표시 이름이나 DB ID를 코드에 고정하지 말고 [정의 데이터](../app/Domains/Common/Category/Definitions)와 code를 기준으로 다룹니다.

CategorySeeder는 단순 append가 아닙니다. 없어진 usage를 정리하고 미참조 항목 삭제 또는 참조 항목 비활성화를 수행할 수 있습니다.
분류 추가 때문에 운영에서 전체 Seeder를 실행하지 않습니다. 대상 전용 Seeder나 변경 범위를 확인합니다.
카테고리의 domain/부모 변경은 일반 수정 계약과 다르므로 트리를 임의 이동시키지 않습니다.

## 이벤트와 미디어

[HospitalEvent](../app/Domains/HospitalEvent)의 등록 방식은 이미지형과 텍스트형입니다.
공통 가격·검수 정보가 같아도 콘텐츠 계약은 다릅니다.

- 이미지형은 페이지 이미지와 옵션 등 해당 입력을 사용합니다. 텍스트형은 시술 대상·장점·전후사진을 사용합니다.
- 전후사진은 선택 입력이지만 한 세트는 전/후 모두 있어야 합니다. 최대 4세트, JPG/PNG, 파일당 5MB입니다.
- before_photo/after_photo 컬렉션의 같은 정렬 순서가 한 쌍입니다.
- 수정의 `before_after_photos`는 전체 순서 목록입니다. 누락하면 유지, 빈 배열이면 제거합니다. multipart의 빈 배열 표현도 기존 Request 계약을 따릅니다.
- 새 업로드와 기존 media_id는 동시에 사용하지 않습니다. 기존 파일은 현재 이벤트 또는 허용된 복제 원본 소유인지 검증하고 중복 사용을 막습니다.
- 이미지형 전환 시 텍스트형 전후사진을 남겨 혼합하지 않습니다. 복제는 원본 삭제에 영향받지 않게 독립된 파일을 만듭니다.
- `doctor_assignments: []`는 연결 해제입니다. 병의원이 바뀌면 의료진 필드가 생략돼도 기존 연결의 소유권을 다시 확인합니다.
- `side_effects`의 null은 제거, 필드 생략은 유지입니다. PATCH의 null·생략·빈 배열을 같은 의미로 바꾸지 않습니다.
- 상담신청단가의 미입력 기본값과 0은 다릅니다. 현재 최소 단가보다 작은 입력을 허용하지 않습니다.
- 옵션은 시술(TREATMENT)의 계약입니다. 기획전 추가를 이유로 자동 확장하지 않습니다.
- 미리보기 context에는 공개용 병의원 장점·의료진 정보만 전달합니다. 면허증·인증 이메일·계좌 정보를 섞지 않습니다.

운영 히스토리는 썸네일·전후사진 모두 서버 생성 파일명으로 기록합니다.
업로드 UI에서 원래 선택한 이름을 보여주는 것과 이미 저장된 변경 이력의 파일명 규칙은 구분합니다.
민감 파일의 저장·다운로드·삭제는 [운영 절차](operations.md)를 따릅니다.

이벤트 상담신청 DB 생성은 이벤트 행을 먼저 잠근 뒤 신청 가능 여부와 기존 신청을 다시 확인합니다.
동시 요청의 신규/중복 판정을 사전 조회만으로 확정하지 않습니다.

## 광고 구좌

[HospitalEventAd](../app/Domains/HospitalEventAd)는 조회 캘린더와 실제 예약 가능 검사를 분리합니다.

- 승인·등록·기간 변경은 공통 booking lock 행을 먼저 획득하고 정원과 겹침을 재확인합니다.
- 아직 예약이 없는 구좌도 보호해야 하므로 기존 예약 행만 잠그는 방식으로 바꾸지 않습니다.
- 구좌 수, 주간 시작일, 판매 마감은 현재 기간 계산·검증 코드를 사용합니다. 시술과 다른 그룹의 기준이 다를 수 있습니다.
- 캐시된 가능 여부는 화면 안내일 뿐입니다. 쓰기 시 병의원·이벤트 상태, 이미지와 기간 조건을 다시 검증합니다.
- 광고 진행 상태는 검수와 날짜로 계산되는 값입니다. 화면 라벨을 새로운 저장 enum으로 추가하지 않습니다.

## 병의원 프로모션

[HospitalPromotion](../app/Domains/HospitalPromotion)은 병의원 파트너 화면의 LEFT/RIGHT 각각 1~3번 고정 슬롯입니다. `start_date`/`end_date`는 필수 유한 KST 날짜이며 양 끝을 포함합니다. `progress`는 서버의 Asia/Seoul 날짜로 계산하고 저장 입력을 거절합니다. 같은 슬롯의 기간 중복은 INACTIVE도 포함해 금지합니다. 저장은 이전/새 슬롯의 영구 참조 행을 정렬해 잠근 뒤 프로모션 행을 잠그고 겹침을 다시 검사합니다.

- 기본 상태는 INACTIVE입니다. `beaulab.hospital_promotion.show/create/update/status_update`를 검사합니다. 기본 admin은 조회·생성·수정, staff/dev는 조회, super_admin은 상태 변경까지 갖습니다. 상태가 실제로 달라질 때만 상태 권한이 필요하며, 기존 ACTIVE 레코드의 좌우·슬롯·기간 변경은 미래/종료 건도 상태 권한이 필요합니다.
- 신규 생성은 잠금을 얻은 뒤 한국 시간 기준 오늘 이전의 `start_date`를 422 `errors.start_date`로 거절합니다. 오늘·미래 시작은 허용하며 기존 건 수정에는 이 신규 날짜 제한을 적용하지 않습니다. 기간 순서·중복과 상태 권한 검증은 수정에도 그대로 적용합니다.
- PATCH에는 상세 DTO의 `updated_at`을 그대로 `expected_updated_at`으로 보냅니다. 잠금 아래 불일치는 422 `errors.expected_updated_at`, 기간 겹침은 422 `errors.slot`과 `일정이 겹치는 프로모션이 있습니다. 확인 바랍니다.` 및 충돌 일정 `availability`로 반환합니다. 파일만 변경해도 마이크로초 정밀도의 편집 토큰이 바뀌며 클릭수는 토큰을 바꾸지 않습니다.
- 배너는 PNG/JPG/JPEG/WEBP 10MB 이하이며 생성 필수, 수정 생략 시 유지, null 삭제는 불가합니다. 비율은 제한하지 않습니다. HTML은 공통 sanitizer로 저장·조회하고 정제 후 빈 본문도 거절합니다.
- 에디터 업로드는 `promotion_id`를 보내도 임시 Media입니다. 경로는 `hospital-promotion/editor-images/temp/{staff_id}/uploads/...`, collection은 `hospital_promotion_editor_temp`입니다. 본인·이 도메인의 24시간 미만 임시 업로드 또는 현재 프로모션 소유 이미지만 허용하며 외부/다른 도메인/다른 프로모션 이미지 재사용은 거절합니다. `promotion_id`로 묶은 업로드는 해당 건에서만 확정합니다. 저장 성공 응답의 정규화된 본문을 사용합니다.
- 저장 중 이미지 확정·제거와 업무/파일/공개여부 히스토리는 같은 트랜잭션입니다. 정리는 임시 Media만 논리 삭제하고 공통 파일 삭제 대기 기록을 남깁니다. 롤백된 파일은 staging manifest로 회수하며, `media:cleanup-files`는 만료된 프로모션 임시 Media도 정리합니다. 파일 히스토리는 서버 생성 파일명을 기록합니다.

`2026_09_11_100000_create_hospital_promotions.php`는 테이블 2개와 슬롯 참조 행 6개만 생성합니다. 권한 4개와 기본 역할 매핑은 다른 도메인처럼 `AccessPermissions`·`AccessRoles` 및 기존 `AuthorizationSeeder`에서 관리하며 권한 전용 마이그레이션은 사용하지 않습니다. 신규 개발 DB의 초기화와 달리 기존 DB에서는 사용자 지정 권한을 덮어쓰지 않도록 필요한 권한만 확인·반영해야 합니다. Factory도 같은 권한 정의를 사용합니다.

집계 컬럼은 `click_count`입니다. 초기 개발 버전의 `view_count`가 남은 DB는 대상·스키마를 확인하고 해당 컬럼만 rename하여 기존 값과 편집 토큰을 보존합니다. 기존 생성 migration 수정은 이미 적용된 DB를 자동 변경하지 않으며, 이 변경을 위해 초기화하거나 migration을 재실행하지 않습니다.

DB 대상을 확인한 뒤 승인된 환경에서 적용할 테이블 생성 파일은 다음과 같습니다. 다른 pending migration을 함께 적용하지 않습니다.

```sh
php artisan migrate --path=database/migrations/2026_09_11_100000_create_hospital_promotions.php
```

rollback은 이 기능의 테이블 2개만 제거하며 역할·권한이나 공통 Media·히스토리·물리 파일을 임의 삭제하지 않습니다. 업무 데이터 생성 이후에는 먼저 백업과 파일·이력 보존 범위를 확인해야 합니다.

## 영상 동의여부 목록

- 직원 `GET /api/v1/staff/videos/consents`는 `beaulab.video.show` 권한으로 삭제되지 않은 전체 병의원을 조회합니다. 허용일 기간, 분과, 병의원 운영 상태, HID·병의원명 검색과 페이지네이션을 지원합니다.
- 허용일은 `hospitals.video_consented_at`입니다. 기록이 없으면 null이며 병의원 생성일·영상 등록일로 추정하지 않습니다. 현재는 목록만 구현하며 동의 등록·철회 API, 메인 노출 수는 포함하지 않습니다.
- 총 동영상은 삭제되지 않은 소속 영상 수, 노출동영상은 영상 정상노출 summary와 같은 조건의 수입니다. 병의원 운영 상태와 허용일은 별도 정보이며 이 집계에 추가 조건으로 섞지 않습니다. 실제 앱 노출 권한 판정 API를 대신하는 목록이 아닙니다.
- 컬럼과 인덱스는 기존 `0001_01_01_000004_create_hospitals_table.php`에 정의합니다. 이미 적용된 DB에는 해당 파일 수정만으로 반영되지 않습니다. 대상을 확인한 뒤 nullable 컬럼과 `hospitals_deleted_video_consent_id_idx`만 추가하고 기존 날짜를 임의로 채우거나 DB를 초기화하지 않습니다.

## 게시물·공지

- Talk, HospitalReview, HospitalEvaluation과 각 댓글의 소유권·공개 조건은 각 도메인에 남깁니다.
- 병의원 평가의 평점은 항목별 값과 별도 집계 규칙을 따릅니다. 병의원 누적 평점에는 정상 공개 평가만 반영하며, 상태 변경·삭제·복구 때 재집계 경로도 확인합니다.
- [Notice](../app/Domains/Notice)는 채널·공개 여부·상단공지·첨부파일이 기준입니다. 신규 기본은 비공개이며 기간·팝업·무기한 게시 기능을 다시 전제하지 않습니다.
- 공지의 등록 관리자는 작성 직원입니다. 마지막 수정자를 등록자로 덮어쓰지 않습니다.
- 공지/FAQ HTML은 저장 및 기존 콘텐츠 조회 때 허용 목록으로 정제합니다. 에디터 임시 파일은 직원별 소유 경로를 확인합니다.
- FAQ의 분류·정렬은 공지와 다릅니다. 편집기만 같다고 같은 도메인으로 합치지 않습니다.

## 신고와 경고

[ContentReport](../app/Domains/Common/ContentReport)의 구조는 접수, 신고 항목, 대상의 현재 처리 상태를 분리합니다.

- Report는 접수 1건, Item은 실제 대상, State는 대상별 현재 상태입니다.
- 같은 신고자·같은 대상의 중복은 Item 기준으로 막습니다. 여러 항목을 묶어 신고해도 우회할 수 없어야 합니다.
- 대상 State를 먼저 잠근 뒤 중복 확인·접수·집계를 처리합니다. MySQL에서 잠금 전 읽기 스냅샷으로 집계하지 않습니다.
- 기본 자동 조치 기준은 최근 1시간 10건이며 정상노출 처리 시점 이후의 유효 신고를 계산합니다. 재노출 누적 예외와 영상의 72시간 접수 처리 등은 대상별 Action 규칙을 유지합니다.
- 채팅 메시지에는 게시물 공개 상태를 새로 덧붙이지 않습니다. 신고가 원본 대화를 전체 사용자에게서 삭제하는 동작은 아닙니다.
- 관리자 미노출은 사유와 경고 정책을 검증합니다. 정상노출 처리에 경고를 붙이지 않으며 영상은 경고 대상에서 제외합니다.
- 영상은 신고접수만으로 정상노출 집계에서 제외하지 않습니다. 공개 상태이고 강제중지·삭제처리(`ADMIN_HIDDEN`)·삭제되지 않은 영상은 신고접수 집계에도 동시에 포함될 수 있습니다. 정상노출 summary와 해당 목록 필터는 같은 조건을 사용합니다.
- 경고 수 변경과 회원 제한 갱신은 동시 요청에 안전해야 합니다. 일반 콘텐츠 수정 API로 신고 제한을 우회하지 못하게 합니다.
- 신고 관리 권한은 원본 수정 권한과 다릅니다. 새 신고 대상을 추가할 때 registry·Policy·라우트·DTO·이력·캐시 갱신을 함께 확인합니다.

임계값만 맞춰도 모든 종류의 신고가 같은 상태로 전이하는 것은 아닙니다.
신고 제한, 수동 계정 정지, 작성자의 비공개 선택을 하나의 상태로 합치지 않습니다.

## 관리자메모와 운영 히스토리

두 기능은 polymorphic 대상으로 여러 도메인에 붙지만 책임은 다릅니다.

| 기능             | 책임                                         |
| ---------------- | -------------------------------------------- |
| AdminNote        | 직원이 작성하는 메모와 메모 자체의 쓰기 권한 |
| OperationHistory | 업무 변경의 before/after 표시와 처리 이력    |
| Activitylog      | 모델 변경 감사 기록. 운영 화면의 이력과 별개 |

[OperationHistory](../app/Domains/Common/OperationHistory)는 저장 구조·대상/Actor 해석·변경값 빌더를 공통 제공하고,
각 도메인의 `*UpdateHistoryRecordAction`은 추적 필드, 라벨, 단위, 관계 정렬을 정합니다. 이 부분은 의도적인 도메인별 코드입니다.

1. 변경 대상 행을 잠그고 변경 전 snapshot을 만듭니다.
2. 같은 트랜잭션에서 업무 데이터를 변경하고 변경 후 snapshot을 만듭니다.
3. 도메인 recorder로 차이를 계산해 공통 생성 Action에 넘깁니다.
4. 실제 차이가 없으면 변경 이력을 만들지 않습니다. 생성 이력은 별도 의미를 갖습니다.

일반 변경과 상태 변경은 `UPDATED`/`STATE_UPDATED`로 구분합니다.
파일은 `fileName()`, 여러 줄 표시값은 `lines()` 등 현재 공통 표시 도구를 사용합니다. 파일명은 서버 저장 경로의 이름이 기준입니다.
과거 이력의 저장된 문구·파일명을 현재 관계값으로 다시 계산하지 않습니다.

새 화면은 changes 배열을 사용하되, 기존 단일 field/before/after 호환 필드를 임의로 제거하지 않습니다.
현재 상태의 처리자·시각은 관련 최신 이력 1건만 조회하고 전체 이력 조회는 페이지네이션합니다.
신고 조치 이력은 원본 콘텐츠에 연결하며, 자동 작업은 Actor를 명확히 구분합니다.

## 메인 배너/팝업 노출설정

- 목록의 `exposure_status`는 종료(ENDED) → 비공개(PRIVATE) → 예정(UPCOMING) → 연결 대상 미노출로 중지(SUSPENDED) → 노출중(ACTIVE) 순서로 판정합니다. 공개여부는 별도 ON/OFF이며 종료된 항목은 OFF여도 노출종료로 표시합니다. 노출중 목록에는 ACTIVE만 포함합니다. 광고의 공개여부는 ON 고정이며 광고기간에 따라 예정/노출중/종료로 표시합니다. 기존 `progress`는 기간 기준 호환 필드로 남기며 목록 배지에는 사용하지 않습니다.

- `BannerExposure`는 메인 팝업, 메인 세로배너, 메인 가로배너와 기타의 상담메모장(`CONSULT_MEMO`)·검색창(`SEARCH`)을 관리합니다. 직원 화면은 배너/팝업과 기타 메뉴로 분리하되 목록·등록 모달·API·권한은 재사용합니다. 직접 등록은 기획전/페이지이며 광고는 `HospitalEventAd`의 승인 데이터를 조회해 합칩니다. 광고를 복제하거나 이 화면에서 비공개·삭제하지 않습니다.
- 현재 노출 수와 무관하게 등록 모달을 열 수 있습니다. 공개 등록·기간 변경·재공개는 선택한 게시기간의 광고 포함 중복 예약이 6개 미만이어야 합니다. 현재 6개가 노출 중이라도 자리가 비는 다음 일정에 등록할 수 있습니다. 비공개 저장은 예약을 점유하지 않으며 재공개 시 용량을 검사합니다. 광고 승인은 이 제한을 적용하지 않으므로 직접 등록 6개 이후 광고 3개가 승인되면 9/6으로 표시합니다. 기존 직접 등록 배너를 자동으로 내리지 않습니다.
- 광고 승인과 직접 등록은 기존 광고 예약 잠금을 공유합니다. 수정·삭제는 `expected_updated_at`, 정렬은 `revision`과 전체 활성 키 집합으로 동시 수정을 감지합니다.
- 기획전은 기존 활성 PROMOTION 카테고리와 소속 이벤트를 선택합니다. 페이지는 병의원/이벤트/공지사항의 ID 또는 HTTPS 외부 주소를 저장합니다. 이벤트 연결의 게시기간은 이벤트 기간 안이어야 합니다.
- 직접 등록은 공개·기간·연결 대상의 현재 노출 조건을 모두 충족해야 노출합니다. 승인 광고는 광고 기간으로 노출하며 직접 등록의 대상 적격 조건으로 숨기지 않습니다.
- `banner_exposures`는 직접 등록, `banner_exposure_placements`는 위치별 순서와 버전, `banner_exposure_metrics`는 `banner:ID`/`ad:ID`별 클릭 요청 수를 저장합니다. 고유 방문자 수가 아닙니다.
- 배포 시 신규 생성 마이그레이션 `2026_10_02_180000_create_banner_exposures.php`와 `beaulab.banner_exposure.show/create/update/delete` 권한 정의를 반영합니다. 기존 광고·카테고리 데이터 초기화는 필요하지 않습니다.
- 기타 위치 `CONSULT_MEMO`, `SEARCH`는 배너 생성 마이그레이션에 포함합니다. 기존 적용 DB는 위치 행 존재 여부를 확인하고 누락된 행만 추가하며, 기존 위치의 순서·버전·등록 데이터를 초기화하지 않습니다. 기타도 위치별 예약 한도, 광고 공개 ON 고정, 연결유형, 게시기간, 클릭수 집계 규칙이 동일합니다.
- 사용자 API는 랜딩 유형/ID/주소를 제공합니다. 실제 앱 화면 전환과 외부 주소 열기는 앱 클라이언트에서 별도로 연결해야 합니다.

## 후기 노출설정

- 성형·쁘띠 및 각 대분류의 전체 탭을 독립 노출 위치로 관리합니다. 카테고리는 기존 후기 usage의 활성 대분류를 재사용하고 검색 시 하위 분류까지 포함합니다.
- 연결 대상은 병의원 후기 하나로 고정합니다. 후기 ID·제목·병의원명 검색을 제공하며 원본 후기의 공개 상태, 신고 차단 여부, 병의원 승인·활성 상태를 등록과 실제 노출 시 확인합니다.
- 게시기간·공개여부·노출순서는 후기 원본과 분리합니다. 동일 위치의 기간 중복 후기 등록을 막고, 공개 예약은 어느 시점에도 6개를 넘을 수 없습니다. 현재 6개여도 빈 미래 기간에는 등록할 수 있습니다. 광고는 합산하지 않습니다.
- 원본 비공개·삭제·차단은 실제 노출에서 즉시 제외되며 예약 항목은 미노출 목록에 유지합니다. 상태는 기존 노출설정의 노출중·노출예정·노출종료·비공개·노출중지 기준을 따릅니다.
- `review_exposure_positions`, `review_exposures`, `review_exposure_metrics`는 `2026_10_06_190000_create_review_exposures.php` 한 파일에서 생성합니다. 기존 후기나 이미지를 복제하지 않습니다. 예약 변경과 순서 저장은 위치 잠금과 낙관적 버전 검사를 사용합니다.
- 목록 이미지는 기존 후기 이미지 요약 조회와 미리보기를 재사용합니다. 담당자는 노출 항목을 등록한 직원이며, 클릭수는 원본 후기 조회수와 별도로 집계합니다.

## 성형·쁘띠 이벤트 노출설정

- `EventExposure`는 성형/쁘띠 각각 상단배너, 성형·쁘띠 HOT이벤트, 카테고리별 상단배너를 관리합니다. 기존 광고의 동일 `placement`와 1:1로 연결하며 카테고리별 위치는 동일한 대분류 ID까지 일치해야 합니다.
- 카테고리는 기존 `HOSPITAL_MEDICAL`의 활성 SURGERY/TREATMENT 대분류를 재사용합니다. 하위 분류 탭은 만들지 않으며 이벤트 검색은 선택한 대분류의 활성 하위 분류까지 포함합니다. 메인/기획전 위치와 연결유형 선택은 없습니다.
- 카테고리별 상단배너의 `전체`는 `category_id` 없이 별도 위치 키로 저장합니다. 등록·순서·공개여부·예약 한도를 개별 대분류와 독립적으로 관리하며 검색 대상은 해당 성형/쁘띠 그룹 전체입니다. 개별 카테고리 광고를 전체 탭에 합산하지 않습니다. 기존 광고 등록은 카테고리 지정이 필수이며, 전체 위치의 광고 조회는 카테고리 연결이 없는 승인 광고만 대상으로 합니다.
- `event_exposures`는 직접 선택한 이벤트·게시기간·공개여부·최초 등록 직원을 저장합니다. `event_exposure_positions`는 `placement[:category_id]`별 순서와 정렬 버전을 저장합니다. 광고는 복제하지 않고 승인된 원본 `HospitalEventAd`를 조회합니다.
- 등록할 이벤트는 승인·공개·정상이며 소속 병의원도 승인·활성이어야 합니다. 미래 이벤트도 선택할 수 있으나 게시기간은 이벤트 기간 안이어야 합니다. 같은 위치·이벤트의 기간 중복 등록은 차단합니다.
- 공개 등록·기간 변경·재공개는 광고 포함 동시 예약이 6개 미만인 기간에만 가능합니다. 이후 광고 3개가 추가 승인되면 9/6까지 표시하며 기존 수동 항목을 내리지 않습니다. 등록 버튼 자체는 현재 개수로 막지 않습니다. 비공개 항목은 예약 개수에서 제외합니다.
- 수동 항목은 원본 이벤트의 현재 노출 조건도 확인합니다. 광고는 공개 토글 ON 고정·비활성이고 광고 기간으로 노출합니다. 이 화면에서 광고 행 수정·삭제는 제공하지 않습니다.
- 노출상태는 메인 배너와 같은 종료→비공개→예정→중지→노출중 기준입니다. 목록 지표는 이벤트 조회수가 아닌 해당 노출 항목의 클릭수입니다. `event_exposure_metrics`의 `(position_key, source_key)`별로 집계하며 전체·개별 카테고리·광고를 구분합니다. 기존 이벤트 조회수는 클릭수로 이관하지 않습니다. 담당자는 수동 등록의 최초 등록 직원, 광고는 원본 담당 직원입니다.
- 클릭 집계 테이블은 이벤트 생성 마이그레이션에 포함합니다. 기존 적용 DB는 `event_exposure_metrics`의 존재 여부와 복합 기본키를 대조하며, 생성 마이그레이션 전체를 재실행하지 않습니다. 사용자 응답의 30분 유효 상대 서명 `click_url`에 앱이 POST해야 증가합니다. 서명·현재 노출 조건·요청 제한을 검사하며 원자적 증가로 동시 클릭의 유실을 방지합니다. 클릭수는 요청 수로, 고유 사용자 수나 과금 지표가 아닙니다.
- 광고와 같은 예약 잠금을 사용하며 수정은 `expected_updated_at`, 정렬은 `revision` 및 현재 전체 활성 키 집합을 검증합니다. 등록·수정·공개여부 변경은 공통 운영 이력과 감사 로그에 기록합니다.
- 배포 시 `2026_10_06_150000_create_event_exposures.php`와 `beaulab.event_exposure.show/create/update` 권한을 반영합니다. 기존 이벤트·광고·카테고리를 초기화하지 않습니다. 사용자 조회 API의 `event_id`로 실제 앱 이벤트 상세 이동을 연결해야 합니다.

## 비대면 상담 DB

현재 구현 범위는 직원의 신청 조회·검수·승인·반려·배정 변경·견적 비교·답변 조회입니다. 회원 신청과 병의원 견적 작성 API/화면, 외부 발송은 아직 없습니다. 배정은 신청 시점에 저장하고 승인은 현재 배정을 확정합니다. 승인 완료를 실제 알림 발송 완료로 해석하지 않습니다.

코드: [RemoteConsultation](../app/Domains/RemoteConsultation), [생성 migration](../database/migrations/2026_09_30_100000_create_remote_consultations_tables.php).

- 신청 정보는 신청 시점의 회원 정보 스냅샷입니다. 회원 계정 변경으로 과거 상담 내용이 바뀌지 않습니다.
- 관심부위는 기존 `HOSPITAL_DOCTOR_SUBJECT` usage의 활성 진료과목 ID를 복수로 연결합니다. 이벤트용 leaf 카테고리를 대신 사용하지 않습니다. 연결 테이블은 당시 과목명도 보관하고, 참조된 카테고리 삭제를 차단합니다.
- 승인상태는 `PENDING`(신청), `REVIEWING`(검수), `APPROVED`(승인), `REJECTED`(반려)입니다. 신청·검수 상태에서 승인 또는 반려할 수 있고, 신청에서 검수로 변경할 수 있습니다. 승인·반려 후 되돌리기는 지원하지 않습니다. 검수·반려도 기존 승인 권한으로 제어하고 운영 이력을 기록합니다.
- 배정은 신청 시점에 선택 병의원 + 랜덤 병의원으로 최대 6곳을 저장하며 승인 전에도 직원 견적 목록에 표시합니다. `RemoteConsultationAssignOnSubmissionAction`은 신청 생성 트랜잭션 안에서 호출하는 내부 처리입니다. 현재 사용자 신청 API는 미구현이며 개발 시더에서 사용합니다. 승인 API는 검수 상태·승인자·승인일만 변경하고 배정을 생성하거나 교체하지 않습니다. 신청/병의원 조합은 유일하며 최초 배정 재호출은 기존 배정을 보존합니다.
- 병의원은 검수 승인·운영 활성·연결 계정 활성이고 신청 과목 중 하나 이상을 보유해야 합니다. 지정 병의원이 조건에 맞지 않으면 전체 승인을 취소합니다. 랜덤 후보가 부족하면 실제 후보 수만 배정합니다. 후보가 전혀 없으면 승인 후 0곳으로 표시되며 자동 재배정 기능은 아직 없습니다.
- 배정 당시 일치 과목, 병의원명, 지정/랜덤 구분, `random-v1`을 저장합니다. 향후 AI 랭킹은 후보 적격 조건을 유지하고 순위 결정만 교체합니다. NDCG는 랭킹 품질 평가 지표입니다.
- 직원은 신청·검수 상태에서 미상담 견적을 삭제하거나 해당 관심 진료과목과 하나 이상 일치하는 활성 병의원을 직접 배정할 수 있습니다. 기존 배정은 검색에서 제외하고 최대 6곳·중복 금지를 서버에서 보장합니다. 직접 배정은 `SELECTED`(선택), `staff-selected-v1`로 기록하며 회원의 원래 선택 내역은 변경하지 않습니다. 승인·배정 추가·삭제는 동일 신청 행을 잠그며 승인 직전 현재 목록의 병의원 자격을 재검증합니다. 승인 이후 편집은 금지합니다. 병의원관리자 수신 API·알림은 아직 없으므로 승인 확정과 실제 전달 연동을 구분해야 합니다.
- 견적은 병의원별 `WAITING`/`ANSWERED`로 구분합니다. 답변 수는 `ANSWERED` 병의원 수입니다. 미발송 답변과 금액은 조회 응답에서 숨깁니다.
- 견적에는 대상 과목 목록, 총 예상비용 1개, 통합 답변 `answer` 1개, 추천 이벤트 스냅샷 목록을 보관합니다. 과목별 금액 합산은 하지 않습니다. 개발 시더는 해당 병의원 기존 이벤트를 최대 3개 연결하며 이미 등록된 추천은 유지합니다.
- 회원 이미지와 스타일 이미지는 공통 Media의 비공개 컬렉션입니다. 회원 이미지 슬롯은 `FRONT`, `SIDE`, `ANGLE_45`, `OTHER`, 스타일 이미지는 정렬 순서로 표시합니다. 승인 시 회원 이미지가 최소 1장인지 확인합니다.
- 승인 권한은 `beaulab.remote_consultation.approve`, 조회는 `beaulab.remote_consultation.show`입니다. 기존 상태 변경 권한 정책에 따라 기본 승인 권한은 최고관리자에게 부여합니다. 승인자·시각과 운영 이력을 기록하며 이미지·문의 원문을 승인 로그에 복제하지 않습니다.

후속 작성 기능 구현 시 서버에서 추가로 검증해야 합니다: 회원 이미지 1~~4장 및 슬롯 중복 금지, 스타일 이미지 0~~4장, 특이사항 허용값, 지정 병의원 0~~6곳, 승인된 배정의 병의원 소유권, 병의원 현재 진료과목과 신청 과목의 교집합 내 견적 대상, 총액 범위, 자 병의원 이벤트만 0~~3개 추천, 답변 필수 범위와 재수정 정책. 현재 조회 전용 견적 모델의 JSON 필드 자체가 이 입력 규칙을 보장하지는 않습니다. 회원 동의·보관/파기 정책과 승인 후 병의원 정지·과목 변경·재배정 정책도 실제 서비스 개방 전에 확정해야 합니다.
