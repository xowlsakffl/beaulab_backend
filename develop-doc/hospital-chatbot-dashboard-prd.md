## 0. 확정된 제품 정책

1. 대시보드는 **뷰랩스 내부 관리자 전용**이다. 병의원 화면에는 아무것도 노출하지 않는다.
2. 지표는 두 출처로 나뉜다. **상담 지표**는 `hospital_chatbot_consultations`·`_messages`에서, **이용 지표**(열람·클릭·전환)는 새로 만드는 `hospital_chatbot_events`에서 낸다. 두 출처를 한 숫자 안에서 섞지 않는다.
3. 이용 이벤트는 **SDK가 이미 내보내는 `onEvent`**를 호스트(hospital-web)가 받아 서버로 보낸다. SDK 본체는 바꾸지 않고 의존성 0 원칙을 지킨다.
4. 이벤트 수집은 **챗봇 동작에 절대 영향을 주지 않는다.** 전송 실패는 조용히 버린다. 재시도·큐·오프라인 저장은 하지 않는다.
5. 이벤트에는 **병의원 ID·병의원 계정 ID·Q&A ID·화면 경로**만 남긴다. 이름·메시지 본문·IP·User-Agent는 남기지 않는다.
6. 원본 이벤트는 **180일** 보관하고 매일 지운다. 일별 합산 표는 MVP에서 만들지 않는다. 조회가 느려지면 그때 만든다(§12).
7. 기간은 **요청 시각(`requested_at`) 또는 이벤트 시각 기준, `Asia/Seoul` 날짜**로 자른다. "지금 대기 중"만 기간과 무관한 현재 값이다.
8. 상담원별 처리 현황은 대시보드에 **넣지 않는다.** 상담 관리 화면의 상담원 ID 검색으로 본다(2026-10-07 결정).
9. 수집은 대시보드보다 **먼저 배포**한다. 데이터는 거꾸로 못 모은다.
10. 작업 브랜치는 **`master`에서 분기**한다(2026-10-08 결정). `AGENTS.md`의 `feat/hospital-chatbot` 기준은 그 브랜치가 master에 통합된 뒤라 이 작업에는 적용하지 않는다.
11. 프론트에는 **테스트 코드를 두지 않는다**(프론트 `AGENTS.md`). 린트·타입 검사·빌드·브라우저 수동 확인으로 검증하고 확인하지 못한 흐름을 PR에 적는다. 백엔드는 수집 API·집계 Query에 테스트를 쓴다.

아래 세부 항목과 위 정책이 충돌하면 이 섹션을 우선한다.

# 1. 문서 목적

클라이언트가 2026-10-07에 요청한 대시보드 항목 네 가지를 검토해 **되는 것·안 되는 것·먼저 깔아야 하는 것**을 가르고, 되는 것을 구현 가능한 수준까지 적는다.

| 클라이언트 요청                                   | 판단            | 근거                                                                     |
| ------------------------------------------------- | --------------- | ------------------------------------------------------------------------ |
| 인기 질문 Top 10 (버튼 클릭 순위)                 | **이 문서로 됨** | 질문 클릭을 서버에 안 남기고 있었다. 이벤트 수집(§10)을 깐다              |
| 병의원별 버튼 클릭 비교                             | **이 문서로 됨** | 같은 이벤트에 병의원 ID가 실린다                                            |
| 최종 액션 버튼 클릭수 (전화 걸기 / 예약 링크)     | **범위 밖**      | 챗봇에 그 버튼이 없다. 답변은 텍스트다(상위 PRD SDK-S03). 기능 추가가 선행 |
| 미등록 키워드 Top 10 (자유 입력)                  | **범위 밖**      | 자유 입력창이 없다(상위 PRD SDK-S02 "자유 입력 없이"). 정책 변경이 선행    |

범위 밖 둘은 §18에 남긴다.

# 2. 배경

챗봇은 2026-09-29 기준 Phase 2~6이 통합 브랜치에 들어갔고, 상담 관리 화면까지 클라이언트 요청으로 합쳐졌다. 다음 질문은 "**얼마나 쓰이나, 어디서 막히나**"다.

지금 DB에는 상담 한 건마다 요청·연결·종료 시각, 사유, 담당, **요청 직전에 보던 Q&A**가 남는다. 이것만으로 요청량·연결률·대기 시간·상담을 유발한 질문은 바로 나온다. 반면 **챗봇을 몇 번 열었는지, 어떤 질문을 몇 번 봤는지**는 아무 데도 남지 않는다. SDK가 `opened`·`question-selected` 이벤트를 호스트에 흘려보내긴 하지만 받는 곳이 없다.

# 3. 목표와 성공 조건

## 3.1 제품 목표

- 운영자가 **매일 아침 한 화면**에서 어제의 챗봇 상태를 30초 안에 파악한다.
- Q&A 담당자가 **어느 답변부터 고쳐야 하는지**를 숫자로 안다.
- 클라이언트에게 **"챗봇이 상담 N건을 줄였다"**를 수치로 말할 수 있다.

## 3.2 성공 조건

| 조건                                                                                   | 측정                                 |
| -------------------------------------------------------------------------------------- | ------------------------------------ |
| 대시보드 첫 로드가 30일 범위에서 2초 안에 끝난다                                        | 운영 DB 크기 기준 응답 시간 측정       |
| 이벤트 수집이 켜진 뒤 SDK 열람·질문 클릭·상담 요청이 빠짐없이 깔때기에 잡힌다            | 브라우저 조작 N회 → 대시보드 N건 일치  |
| 수집 서버가 죽어도 챗봇은 평소처럼 동작한다                                              | 수집 엔드포인트 차단 후 E2E 통과       |
| 상담 지표 숫자가 상담 관리 화면의 조건 검색 결과와 같다                                  | 같은 기간·조건으로 두 화면 대조        |

# 4. 범위

## 4.1 In Scope

- 내부 관리자 메뉴 `병의원 챗봇 → 대시보드` 화면 하나 (ADM-D01)
- 상담 지표: 요청 수, 연결률, 대기 초과율, 대기 시간, 첫 응답 시간, 상담 시간, 지금 대기 중, 일별 추이, 요일×시간대, 상담 유발 질문 Top 10, 병의원별 요청 Top 5
- 이용 지표: 챗봇 열람 수, 질문 클릭 수, 인기 질문 Top 10, 병의원별 클릭 비교, 깔때기(열람→질문→상담)와 전환율, 질문별 상담 전환율
- 이용 이벤트 수집 엔드포인트와 테이블, 보관 기간 정리 커맨드
- hospital-web 호스트의 이벤트 전송 어댑터
- 대시보드 집계 엔드포인트 하나

## 4.2 Out of Scope

- 상담원별 처리 현황 (정책 8)
- 전화·예약 등 **액션 버튼**과 그 클릭 집계 — 챗봇에 버튼 자체가 없다
- **자유 입력** 검색과 미등록 키워드 — 자유 입력이 없다
- 상담 첫 메시지 키워드 분석 — 한국어 형태소 처리 품질이 보장되지 않는다
- 만족도 — 설문 기능이 없다
- 병의원 화면용 통계, 외부 분석 툴(GA 등) 연동, 알림·임계치 경보
- 대시보드 내보내기(CSV/이미지)
- 일별 합산 표(롤업) — 느려지면 그때(§13)

## 4.3 다른 화면과의 경계

- 상담원별·병의원별·질문별 **상세 목록**은 대시보드가 아니라 **상담 관리 화면**의 조건 검색이 맡는다. 대시보드의 표 행을 누르면 그 조건으로 상담 관리 화면을 연다(병의원 ID, 상담 ID 등 이미 있는 조건만).
- 로그 기반 운영 지표(Claim 충돌, 발행 실패, 5분 gauge)는 **이 대시보드에 넣지 않는다.** 그건 로그 수집기의 일이다(상위 PRD 16.6).

# 5. 용어

| 용어          | 뜻                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------- |
| 상담 지표     | `hospital_chatbot_consultations`·`_messages`에서 계산하는 값                                  |
| 이용 지표     | `hospital_chatbot_events`에서 계산하는 값                                                     |
| 열람          | 병의원 사용자가 챗봇 런처를 눌러 패널을 연 것. `WIDGET_OPENED`                                   |
| 질문 클릭     | 질문 목록에서 질문 하나를 눌러 답변을 본 것. `QNA_VIEWED`                                      |
| 상담 요청     | `상담원 연결`을 눌러 상담이 생성된 것. 이벤트가 아니라 상담 테이블의 행                           |
| 깔때기        | 열람 → 질문 클릭 → 상담 요청 세 단계의 건수와 비율                                              |
| 상담 유발 질문 | 상담 요청 직전에 보고 있던 질문. `consultations.context_qna_id`                                |
| 연결          | 상담원이 Claim에 성공해 `connected_at`이 찍힌 것. 이후 종료돼도 "연결됐던 것"으로 센다           |

# 6. 전제와 구현 제약

- 백엔드는 기존 모듈 구조(`app/Modules/Staff`, `app/Modules/Hospital`, `app/Domains/HospitalChatBot/{Actions,Queries,Models,Support}`)와 `ApiResponse::success($data, $meta)` 규약을 따른다. 집계는 충전금 대시보드(`HospitalWalletDashboardGetForStaffAction`·`...ForStaffQuery`·`...ForStaffRequest`)와 같은 모양으로 둔다.
- 권한은 기존 `common.access`를 쓴다. 새 권한을 만들지 않는다(상위 PRD 4.3).
- 프론트는 staff-web의 `DashboardCard`·`DashboardSummary`·`useSyncCurrentPageQuery`·`DateRangeFilterDropdown`과 `lib/<도메인>/dashboard.ts` 패턴(충전금 대시보드) 등 **있는 것**을 쓴다. 차트는 `@beaulab/ui-admin`의 apexcharts 래퍼(`DoubleBarChart`, `LineChartOne` 등)를 쓰고, 히트맵만 같은 방식의 래퍼를 `ui-admin/chart`에 하나 추가한다. 다른 차트 라이브러리는 추가하지 않는다.
- SDK 패키지(`packages/hospital-chatbot-sdk`)는 **변경하지 않는다.** 필요한 이벤트는 이미 `onEvent`로 나온다: `opened`, `question-selected`, `consultation-requested`.
- MySQL 8. 인덱스 이름 64자 제한, Partial Unique Index 없음(상위 PRD와 같은 제약).
- 예상 규모: 병의원 사용자 DAU 50 미만. 이벤트는 하루 수천 건을 넘지 않는다. 그래서 롤업 없이 원본 집계로 시작한다.

# 7. 사용자 흐름

## 7.1 운영자

1. `병의원 챗봇 → 대시보드`를 연다. 기본 기간은 **최근 30일**이다.
2. 카드 여섯 개와 깔때기로 상태를 읽는다. "지금 대기 중"이 0이 아니면 상담 관리로 간다.
3. 일별 추이에서 주황(대기 초과)이 두드러진 날을 찾아 요일×시간대에서 몰리는 시간을 확인한다.
4. 기간을 바꾸거나 새로고침한다. 기간은 URL에 실려 공유된다.

## 7.2 Q&A 담당자

1. 「상담을 많이 유발한 질문 Top 10」 위에서부터 본다. 클릭 수 대비 상담 전환율이 높은 질문이 **답변이 부족한 질문**이다.
2. 「인기 질문 Top 10」에서 많이 보는데 상담으로 안 가는 질문은 **잘 된 답변**이다. 손대지 않는다.
3. 행을 누르면 Q&A 관리 화면의 그 질문으로 간다.

## 7.3 이벤트가 쌓이는 흐름

1. 병의원 사용자가 챗봇 런처를 누른다 → SDK `onEvent({type:"opened"})` → 호스트가 `WIDGET_OPENED`를 서버로 보낸다.
2. 질문을 누른다 → `question-selected` → `QNA_VIEWED` + `qna_id`.
3. `상담원 연결`을 누른다 → 상담이 생성된다. **이벤트를 따로 보내지 않는다.** 깔때기 마지막 단계는 상담 테이블에서 센다. 같은 사실을 두 곳에 적지 않는다.
4. 서버는 받은 시각을 `occurred_at`으로 적는다. 클라이언트 시계를 믿지 않는다.
5. 전송이 실패하면 호스트는 아무것도 하지 않는다. 사용자는 모른다.

# 8. 화면 요구사항

## ADM-D01. 대시보드

**위치** — 내부 관리자 `병의원 챗봇` 메뉴 첫 항목. 경로 `/hospital-chatbot/dashboard`. 권한 `common.access`.

**필터 (상단 한 줄)**

| 항목   | 요구                                                                                        |
| ------ | ------------------------------------------------------------------------------------------- |
| 기간   | 프리셋 `오늘` `최근 7일` `최근 30일` + 직접 선택. 기본 최근 30일. 최대 366일                   |
| URL    | `?from=Y-M-D&to=Y-M-D`. 기본값이면 비운다. 뒤로가기·새로고침·링크 공유가 그대로 되어야 한다       |
| 새로고침 | 버튼 하나. 자동 갱신은 「지금 대기 중」 카드만 30초 주기                                       |

**1행 — 카드 7개**

# 9. 지표 정의

모든 상담 지표의 모집단은 **기간 내 `requested_at`인 상담**이다. 상태나 종료 시각으로 자르지 않는다. 그래야 카드끼리 분모가 같다.

| 지표                 | 정의                                                                                                   | 비고                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------ |
| 요청 수              | `COUNT(*)`                                                                                             |                                            |
| 연결 수              | `connected_at IS NOT NULL`                                                                              | 종료·진행 중 모두 포함                      |
| 연결률               | 연결 수 ÷ 요청 수                                                                                       | 요청 0이면 `—`                              |
| 대기 초과 수         | `close_reason = 'WAITING_TIMEOUT'`                                                                      |                                            |
| 대기 초과율          | 대기 초과 ÷ 요청 수                                                                                     |                                            |
| 사용자 취소 수       | `close_reason = 'USER_CANCELED'`                                                                        |                                            |
| 진행 중 수           | `status IN ('WAITING','CONNECTED')`                                                                     | 일별 차트의 네 번째 구간                    |
| 대기 시간            | 연결된 건의 `connected_at − requested_at`                                                               | 중앙값·P90. 연결 안 된 건은 제외             |
| 첫 응답 시간         | 연결된 건 중 상담원이 **직접 친** 메시지(`sender_type='AGENT'`, `message_type='TEXT'`, `client_message_id`가 `greeting:`으로 시작하지 않음)가 1건 이상인 건의 `MIN(messages.created_at) − connected_at` | 연결 시 자동 인사가 AGENT 메시지로 먼저 들어가므로 그걸 빼지 않으면 전부 0초다. 인사만 있는 건은 제외 |
| 상담 시간            | `status='ENDED'`인 건의 `ended_at − connected_at`                                                       | 카드엔 없고 표·hover에만                    |
| 지금 대기 중         | **현재** `status='WAITING'` 건수와 `NOW() − MIN(requested_at)`                                            | 기간 무관                                   |
| 직전 기간 대비       | 같은 길이의 바로 앞 기간 요청 수와 비교한 증감 %                                                          | 앞 기간이 0이면 `—`                          |
| 상담 유발 질문       | `context_qna_id`별 `COUNT(*)`. NULL(질문 안 보고 요청)은 제외하되 **별도 한 줄로 "질문 없이 요청 N건"**     | 질문 본문은 `qnas`를 조인. 삭제된 Q&A도 조인 |
| 병의원별               | `hospital_id`별 요청 수·연결률. 이름은 `hospital_name_snapshot` 최신 값                                     |                                            |
| 열람 수              | `events.event_type='WIDGET_OPENED'` 건수                                                                 | 이용                                       |
| 질문 클릭 수         | `events.event_type='QNA_VIEWED'` 건수                                                                    | 이용                                       |
| 인기 질문            | `QNA_VIEWED`의 `qna_id`별 건수                                                                           | 이용                                       |
| 챗봇 → 상담 전환율   | 요청 수 ÷ 열람 수                                                                                        | 열람이 0이거나 수집 전이면 `—`               |
| 질문별 상담 전환율   | 그 질문의 상담 유발 건수 ÷ 그 질문의 클릭 수                                                              | 클릭 0이면 `—`                               |

중앙값·P90은 SQL `PERCENTILE`이 없는 MySQL 8에서 **정렬 후 오프셋**으로 구한다. 건수가 많아지면 `WINDOW` 함수로 바꾼다.

# 10. 이용 이벤트 수집 요구사항

## EVT-01. 이벤트 종류

| `event_type`     | 언제                                | 실리는 값                              | SDK 원천 이벤트      |
| ---------------- | ----------------------------------- | -------------------------------------- | -------------------- |
| `WIDGET_OPENED`  | 런처를 눌러 패널이 열릴 때           | `source_page_path`                      | `opened`             |
| `QNA_VIEWED`     | 질문을 눌러 답변 화면이 열릴 때      | `qna_id`, `source_page_path`            | `question-selected`  |

상담 요청은 이벤트로 보내지 않는다(§7.3). 분류(폴더) 클릭도 MVP에서 보내지 않는다. 종류를 늘릴 땐 이 표에 먼저 적는다.

## EVT-02. 호스트 전송 규칙 (hospital-web)

- `HospitalChatbotSdkMount`가 `onEvent`를 구독해 위 두 종류만 서버로 보낸다. 나머지 이벤트는 무시한다.
- **한 건씩 즉시** 보낸다. 묶기·지연·재시도는 하지 않는다. 규모가 작다.
- `fetch(..., { keepalive: true })`로 보내 페이지 이동 중에도 유실을 줄인다. 응답은 기다리지 않고 실패는 무시한다.
- 같은 `qna_id`의 `QNA_VIEWED`가 **2초 안에 반복**되면 두 번째는 보내지 않는다(더블클릭 방지). `WIDGET_OPENED`는 열 때마다 보낸다.
- 인증은 기존 병의원 세션 쿠키 그대로다. 별도 키·토큰 없음.

## EVT-03. 서버 수신 규칙

- 엔드포인트 `POST /api/v1/hospital/hospital-chatbot/events` (§12.1). 병의원 액터 미들웨어를 탄다.
- 본문은 **배열**로 받되 한 번에 최대 20건. 1건만 보내도 배열이다. 나중에 묶음 전송으로 바꿔도 계약이 안 바뀌게.
- 검증: `event_type`은 EVT-01의 값만, `qna_id`는 `QNA_VIEWED`일 때 필수이고 존재하는 Q&A(소프트 삭제 포함)여야 한다, `source_page_path`는 255자 이하 선택.
- 검증 실패는 **422로 응답하되 로그만 남긴다.** 클라이언트가 어차피 무시하므로 알림 수준으로 올리지 않는다.
- `hospital_id`·`account_hospital_id`는 **세션에서** 꺼낸다. 본문의 값은 받지 않는다.
- `occurred_at`은 서버 수신 시각이다.
- 저장 성공은 `202 Accepted`, 본문 `{ accepted: n }`.
- 분당 **120건/계정** 레이트리밋. 넘으면 429. 정상 사용에서 넘을 일이 없고, 넘으면 스크립트다.

## EVT-04. 보관

- `hospital-chatbot:prune-events` 커맨드가 **180일**보다 오래된 행을 매일 새벽 지운다. 한 번에 1만 건씩 끊어서.
- 기간은 `config('hospital_chatbot.events_retention_days', 180)`.

# 12. API

## 12.1 이벤트 수신 — 병의원

`POST /api/v1/hospital/hospital-chatbot/events`

```json
[
  { "event_type": "WIDGET_OPENED", "source_page_path": "/dashboard" },
  { "event_type": "QNA_VIEWED", "qna_id": 17, "source_page_path": "/dashboard" }
]
```

응답 `202` — `{ "data": { "accepted": 2 } }`. 실패 코드: `422`(검증), `429`(한도), `401`(세션 없음).

## 12.2 대시보드 — 내부 관리자

`GET /api/v1/staff/hospital-chatbot/dashboard?from=2026-09-08&to=2026-10-07`

**한 번의 호출로 화면 전체**를 돌려준다. 카드 7개를 위해 7번 부르지 않는다.

```json
{
  "data": {
    "period": { "from": "2026-09-08", "to": "2026-10-07", "timezone": "Asia/Seoul" },
    "summary": {
      "requested": 142, "requested_previous": 120,
      "connected": 118, "timed_out": 19, "user_canceled": 5, "active": 0,
      "waiting_seconds": { "median": 100, "p90": 372 },
      "first_response_seconds": { "median": 48, "p90": 190, "sample": 112 },
      "consultation_seconds": { "median": 540, "p90": 1420, "sample": 109 }
    },
    "live": { "waiting": 2, "longest_waiting_seconds": 185, "checked_at": "2026-10-07T09:12:00+09:00" },
    "funnel": { "collected_since": "2026-10-01", "opened": 1240, "qna_viewed": 860, "requested": 142 },
    "daily": [ { "date": "2026-09-08", "ended": 6, "timed_out": 0, "user_canceled": 0, "active": 0 } ],
    "heatmap": [ { "dow": 1, "hour": 10, "count": 7 } ],
    "top_context_qnas": [ { "qna_id": 17, "question": "충전금 환불 받고 싶어요", "requested": 31, "viewed": 410, "deleted": false } ],
    "requested_without_context": 23,
    "top_viewed_qnas": [ { "qna_id": 17, "question": "...", "viewed": 410, "requested": 31, "deleted": false } ],
    "top_hospitals": [ { "hospital_id": 3, "name": "강남 뷰티의원", "requested": 23, "connected": 21, "opened": 180, "qna_viewed": 96 } ]
  }
}
```

- `funnel.collected_since`가 `from`보다 **뒤**면 화면은 깔때기와 전환율을 `수집 시작 전`으로 표시한다. 이벤트가 하나도 없으면 `null`.
- `first_response_seconds.sample`은 표본 수다. 10 미만이면 화면이 숫자 옆에 "표본 N건"을 붙인다.
- `deleted`가 참이면 질문 옆에 `삭제됨` 표시. 행 클릭은 막는다.
- 기간 검증: `from ≤ to`, 366일 이하, 둘 다 `Y-m-d`. 위반은 `422`.
- 권한: `common.access`. 캐시 없음(§13).

# 13. 성능·보관·개인정보

- **성능** — 30일·요청 1만 건·이벤트 10만 건에서 2초 안. 상담 테이블엔 `requested_at` 인덱스가 이미 있고, 이벤트 테이블은 §11.1의 인덱스로 간다. 느려지면 순서대로: (1) 응답 60초 캐시, (2) 일별 롤업 표 `hospital_chatbot_event_daily(date, hospital_id, event_type, qna_id, count)` + 야간 적재. 둘 다 이번엔 안 한다.
- **보관** — 이벤트 원본 180일(EVT-04). 상담 테이블은 건드리지 않는다.
- **개인정보** — 이벤트에 사람을 특정하는 값은 `account_hospital_id`뿐이고 이것도 감사용이다. 대시보드는 계정 단위로 아무것도 보여 주지 않는다. IP·UA·이름·본문은 수집하지 않는다. 180일 뒤 삭제로 보관 최소화 원칙을 지킨다.
- **부하 격리** — 수신 엔드포인트는 INSERT 한 번이다. 실패해도 챗봇 쪽엔 영향이 없고, 대시보드 조회가 느려도 상담에는 영향이 없다(읽기만).
