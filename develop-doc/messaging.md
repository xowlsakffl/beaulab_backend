# 메시징

채팅·알림·SMS는 함께 큐를 쓰지만 저장 의미와 재시도 조건이 다릅니다.
업무상 대상 선정은 호출 도메인, 전달 기록과 전송은 해당 공통 기능이 담당합니다.

## 채팅

[Chat](../app/Domains/Chat)은 현재 일반 사용자 간 1:1 대화입니다. 병의원 상담 채팅이 구현됐다고 해석하지 않습니다.

- 첫 메시지 전송 시 방을 만듭니다. 화면을 열기만 했다고 빈 방을 만들지 않습니다.
- 정렬된 사용자 ID의 match_key unique 제약으로 같은 두 사용자의 중복 방을 방지합니다.
- 활성 계정·참여자·상대방 차단 상태를 검사합니다. 어느 한쪽이 차단했으면 새 메시지를 보내지 못합니다.
- 재시도할 메시지는 동일한 client_message_id를 사용합니다. 이 필드가 없는 요청은 같은 수준의 중복 방지를 기대할 수 없습니다.
- 답장 대상은 같은 방의 메시지여야 합니다. 첨부 개수·형식·크기는 각 Request를 따릅니다.
- 메시지·첨부 연결·필수 알림함 데이터를 함께 커밋합니다. 외부 브로드캐스트 실패로 저장된 메시지를 실패 처리하지 않습니다.

목록은 커서 기반입니다. before_id/after_id를 동시에 사용하지 않으며 초기/과거 조회와 신규 조회의 정렬 방향을 구분합니다.
페이지 번호와 total 기반 목록으로 억지로 통일하지 않습니다.
읽음 커서는 뒤로 이동시키지 않고, 대화 삭제는 사용자별 deleted_until_message_id까지 숨기는 방식입니다. 상대방 대화 기록을 물리 삭제하지 않습니다.

채팅 신고는 같은 방·같은 상대방의 메시지를 묶어 처리하며 이미 신고한 항목과 숨김 범위를 검증합니다.
신고자 측 차단·대화 숨김과 원본 메시지의 전체 삭제는 다른 동작입니다.

### 실시간 전달

채널은 private chat/user이며 [channels.php](../routes/channels.php)에서 실제 참여자와 사용자 ID를 검증합니다.
사용자용 `/api/v1/user/broadcasting/auth`도 인증과 actor:user 경계를 통과해야 합니다.

저장한 메시지의 broadcast_pending과 chat 큐를 사용합니다.
브로드캐스트 Job이 실패하면 저장 성공은 유지하고 Scheduler가 미완료 메시지를 재큐잉합니다.
Reverb는 정확히 한 번 전달을 보장하지 않으므로 클라이언트는 메시지 ID로 중복을 제거합니다.
공유 이벤트의 is_mine을 서버에서 한 사용자 기준으로 고정하지 말고 수신 클라이언트가 발신자 ID로 판단합니다.

## 인앱 알림과 Push

[Notification](../app/Domains/Common/Notification)의 공통 생성 진입점은 CreateNotificationAction입니다.
호출 도메인은 수신자와 업무 payload를 결정하고 공통 계층은 알림함·전달 기록·기기·설정을 관리합니다.

| 데이터                 | 의미                             |
| ---------------------- | -------------------------------- |
| Notification           | 사용자가 읽을 알림함 항목과 집계 |
| NotificationDelivery   | 채널별 전달 상태                 |
| NotificationDevice     | 기기 토큰과 활성 상태            |
| NotificationPreference | 수신 설정                        |

미읽음 집계는 open_aggregation_key의 고유성으로 보호합니다.
읽으면 현재 집계 묶음을 닫고 이후 이벤트는 새 항목으로 만듭니다. 알림 항목 수와 누적 event_count를 혼동하지 않습니다.
IN_APP을 끈 Push 전용 이벤트가 인앱 묶음을 잘못 재사용하지 않도록 채널 구분도 유지합니다.

현재 연결된 대표 업무는 채팅 메시지와 병의원 운영중지 신청·처리입니다.
User의 알림함·실시간 API와 Staff 업무 알림 기록의 제공 범위는 같지 않습니다. Staff 알림 데이터 생성이 별도 결재·알림 UI 완성을 의미하지 않습니다.
EMAIL/WEB 값이나 이메일 수신 설정이 있어도 일반 알림 이메일 발송 전체가 구현된 것은 아닙니다. 계정 인증 메일은 별도 흐름입니다.

Push는 FCM/APNs 설정과 활성화가 필요합니다. 기본 설정만으로 실발송을 보장하지 않습니다.
기기 토큰을 저장할 때 해시로 중복을 판정하고 재등록·로그아웃에 따른 토큰 소유권과 비활성화를 확인합니다.

### 재시도와 부분 성공

- Delivery는 generation, message_snapshot, device_results, lease_token과 처리 만료 시각을 보존합니다.
- 기기별로 전송하며 성공한 기기를 같은 세대에서 다시 보내지 않습니다.
- 429/5xx·일시 예외는 해당 기기를 최대 3회 시도합니다. 영구 오류와 무효 기기 토큰은 분리합니다.
- 이전 워커의 늦은 결과가 새 generation을 덮어쓰지 않도록 임대와 세대를 확인합니다.
- 일부 기기만 성공해도 Delivery는 SENT가 될 수 있습니다. 전체 기기 성공 여부는 device_results로 확인합니다.
- 업체 수락 직후 워커가 종료되면 중복 가능성이 남습니다. provider 호출 횟수와 사용자 알림 개수를 같은 것으로 해석하지 않습니다.

알림함 데이터는 DB에 남으므로 실시간 갱신 누락은 목록 재조회로 복구할 수 있습니다.
중요한 알림함 기록은 업무 트랜잭션 안에서 생성하고, 외부 전달만 커밋 이후로 분리합니다.

## SMS

[Sms](../app/Domains/Common/Sms)는 Batch와 수신자별 Delivery를 저장하고 sms 큐에서 전달합니다.
현재 제공 provider는 log/disabled이며 실제 SMS 업체 연동이 완료된 것은 아닙니다.
log provider 성공은 휴대폰에 문자가 도착했다는 뜻이 아닙니다.

- 호출 도메인이 목적, 대상, 템플릿을 결정합니다. 공통 발송 계층에 병의원 선택 쿼리를 넣지 않습니다.
- 수신자 이름·번호·최종 본문을 발송 시점 스냅샷으로 보존합니다.
- TEXT/VARIABLE로 구성된 메시지에서 병의원명·잔여 포인트는 서버 값으로 치환합니다. 잔여 포인트에는 환불 예약분을 제외합니다.
- Batch 멱등 키와 request_hash로 재요청을 비교합니다. 동일 키·다른 payload는 거부하고 기존 발송을 중복 dispatch하지 않습니다.
- API 성공은 발송 대기 등록입니다. 연락처 누락 등 제외 건수와 최종 전송 실패를 구분해서 보여줍니다.
- 크기는 현재 바이트 계산 및 SMS/LMS 설정으로 검증합니다. 실제 업체 연결 시 해당 업체의 인코딩·길이 기준을 별도로 맞춰야 합니다.

[SMS 설정](../config/sms.php)의 disabled_purposes에는 과거 병의원 휴대폰 인증·비밀번호 재설정 목적이 남아 있습니다.
해당 대기 작업은 SKIPPED 처리하며 휴대폰 인증을 되살리지 않습니다. 계정 인증은 [이메일 흐름](api.md)입니다.
기존 SMS polymorphic 관계 때문에 남은 모델을 현재 가입 기능이라고 해석하거나 데이터 확인 없이 삭제하지 않습니다.

### 실패 복구

PROCESSING이 5분 이상 지속되면 복구 대상으로 판단합니다.
단, provider의 supportsIdempotentRetries 계약이 보장하는 경우에만 불명확한 발송을 재시도합니다.
비멱등 업체에서 이미 수락했는지 모르는 건은 실패로 남기고 업체 결과를 확인해야 합니다.
현재 Job/Action의 재시도 상한과 backoff를 따라야 하며 대기열 전체를 무조건 재전송하지 않습니다.

## 운영에서 확인할 순서

1. 업무 원장 또는 메시지·알림함·Batch가 DB에 생성됐는지 확인합니다.
2. Delivery/기기 결과, broadcast_pending, Job 실패 이유를 확인합니다.
3. Redis 연결, 해당 큐 소비자, 외부 provider 설정·타임아웃을 확인합니다.
4. 중복 가능성을 판단한 뒤 필요한 대상만 재처리합니다.

Horizon과 Scheduler의 실행, 복구 명령의 부작용은 [운영 절차](operations.md)를 따릅니다.
로그에 인증번호·토큰·전체 본문·기기 토큰을 덤프하지 않습니다.
