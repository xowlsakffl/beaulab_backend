# 성능 / 인덱스 / 쿼리 규칙

작성 기준: 2026-07-31

이 문서는 백엔드 성능 변경의 판단 기준과 현재 적용 구조를 정리한다.

## 1. 기본 원칙

- 응답 시간을 추측으로 판단하지 않고 쿼리 수, SQL 실행 시간, 직렬화 시간, 이미지 요청을 분리해 측정한다.
- 목록의 쿼리 수는 행 개수에 따라 늘지 않아야 한다.
- 인덱스는 실제 `where`, `join`, `order by` 조합과 실행 계획을 근거로 추가한다.
- 캐시는 DB 정합성을 대신하지 않는다. 쓰기 완료 후 무효화하고, 최종 검증은 DB transaction과 제약 조건을 기준으로 한다.
- 개발 DB의 적은 데이터에서 빨라도 운영 데이터 분포와 페이지 크기를 함께 검토한다.

## 2. 목록 쿼리

- 관계 표시는 `with()`로 미리 불러오고 건수는 `withCount()` 또는 집계 쿼리를 사용한다.
- 행마다 관계나 건수를 다시 조회하는 N+1 패턴을 금지한다.
- 목록, summary, selector가 서로 독립이면 API 또는 쿼리를 불필요하게 순차 실행하지 않는다.
- 같은 조건을 값만 바꿔 반복 집계하는 경우 `group by` 한 번으로 합칠 수 있는지 먼저 확인한다.
- eager load가 많아 쿼리 수가 커 보이더라도 페이지 크기를 바꿨을 때 쿼리 수가 고정이면 N+1로 단정하지 않는다.

현재 적용 사례:

- Staff 메뉴 N 배지는 신고 대상별 개별 집계 대신 대상 타입 및 후기 분류별 그룹 집계를 사용한다.
- 광고 현황 달력은 주차별 구좌를 반복 조회하지 않고 월에 필요한 승인 광고를 한 번에 조회한 후 메모리에서 구좌별로 묶는다.

## 3. 인덱스

- 외래 키, 다형 관계의 `type + id`, 자주 함께 쓰는 상태와 정렬 컬럼을 우선 검토한다.
- 단일 컬럼 인덱스 여러 개가 복합 조건을 자동으로 대체한다고 가정하지 않는다.
- 중복 인덱스와 쓰기 비용을 함께 확인한다.
- 데이터가 매우 적거나 정렬 정책이 `case` 표현식인 경우, 측정 이득 없이 생성 컬럼과 인덱스를 추가하지 않는다.
- 마이그레이션 정책상 초기 개발 단계의 스키마 변경은 기존 생성 마이그레이션에 반영한다.

## 4. Cache / Redis

- summary와 광고 달력처럼 반복 계산되는 읽기 결과만 캐시한다.
- 캐시 키에는 결과를 바꾸는 도메인, 필터, 날짜, 카테고리를 모두 포함한다.
- 등록, 수정, 상태 변경 성공 후 관련 캐시를 무효화한다.
- 상세 기준은 `develop-doc/cache.md`를 따른다.

## 5. 미디어 전송

- 새 미디어 업로드 디스크는 `config/media.php`의 `MEDIA_DISK`를 사용한다. 기존 행은 각 `media.disk` 값을 유지한다.
- 목록은 `thumb`, 일반 상세는 `medium`, 원본보기는 원본 URL 사용을 우선한다.
- 원본보다 큰 파생 이미지가 만들어지고 원본 해상도도 목표 해상도의 두 배 이하라면 해당 variant를 저장하지 않는다. 화면은 원본으로 fallback한다.
- 랜덤 파일 경로는 내용 변경 시 새 경로가 생성되므로 `MEDIA_CACHE_CONTROL`의 장기 immutable 캐시를 사용할 수 있다.
- S3는 업로드 객체에 Cache-Control 메타데이터가 기록된다. 로컬 `public/storage`는 Nginx, CDN 등 정적 파일 서버에서도 같은 캐시 헤더를 설정해야 한다.
- 이미지 요청 여러 건을 하나의 API 응답에 바이너리로 합치지 않는다. 브라우저 병렬 요청과 HTTP 캐시/CDN을 사용한다.

## 6. 검증 절차

1. 동일 입력으로 변경 전후 응답과 집계 값이 같은지 비교한다.
2. 페이지 크기를 바꾸며 쿼리 수가 증가하는지 확인한다.
3. 캐시 miss와 hit를 따로 측정한다.
4. `EXPLAIN`으로 후보 인덱스 사용 여부와 filesort 범위를 확인한다.
5. PHP 문법, Pint, 애플리케이션 route boot를 확인한다.
6. 프론트는 production build, 목록 재진입, 이미지 네트워크 요청과 layout shift를 함께 확인한다.

로컬 WSL 환경에서는 Windows 브라우저의 `localhost` 포워딩 시간이 API 처리 시간보다 클 수 있다. 서버 내부 `127.0.0.1` HTTP 측정값을 함께 남기고, Windows 경로 수치만으로 쿼리 성능을 판단하지 않는다.
