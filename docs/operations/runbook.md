# 운영 절차와 안전 경계

이 문서는 저장소가 요구하는 실행 조건을 설명합니다. 실제 운영 호스트·배포 방식·프로세스 관리자·백업 보존 기간·복구 목표는 현재 저장소만으로 확인되지 않습니다. 아래를 검증 완료된 운영 배포 매뉴얼로 해석하지 않습니다.

## 배포 전

1. 배포 코드·프론트 API 호환성·DB 스키마 차이를 확인합니다.
2. 실제 연결 대상, APP_KEY 보관, 환경별 DB·Redis·파일·큐 분리를 확인합니다.
3. 암호화값·서명 링크가 있는 환경의 APP_KEY를 교체하지 않습니다.
4. DB 변경이 있으면 데이터·DDL 백업과 복원 절차를 준비합니다.
5. 기존 워커가 새 스키마에 맞지 않는 메시지를 처리하지 않도록 순서를 정합니다.
6. 웹·큐·스케줄러·Reverb와 관련 프론트의 적용·되돌리기 순서를 함께 검토합니다.

현재 생성 마이그레이션 수정 정책은 적용된 DB를 자동 전환하지 않습니다. 운영 DB에서 migrate:fresh로 해결하지 않습니다.

## 프로세스

HTTP, 큐 작업자, 스케줄러, Reverb는 별도 실행 구성입니다. Horizon 전체 시작은 여러 발송 큐를 소비할 수 있습니다. 로컬 특정 기능 확인에는 승인된 전용 큐만 사용합니다.

배포 후에는 장기 실행 워커가 새 코드를 읽도록 정상 종료·재기동을 계획합니다. 진행 중 작업, retry_after, timeout, 메시지 멱등성을 확인하고 임의 강제 종료·전체 재시도를 피합니다.

운영 환경은 HTTPS, APP_DEBUG=false, 정확한 허용 Origin, 제한된 내부 도구 IP·계정이 필요합니다. 서버 secret을 NEXT_PUBLIC 변수에 넣지 않습니다.

## 장애별 확인 순서

| 현상                 | 확인                                                         |
| -------------------- | ------------------------------------------------------------ |
| HTTP 오류            | traceId, 오류 코드, 해당 주체·권한·대상, 민감값 제거한 로그  |
| 로그인·새로고침 실패 | 세션 저장소·CSRF·Origin·쿠키·동시 요청, 서버 오류와 401 구분 |
| 알림 없음            | 발행 이벤트·수신 자격·수신 설정·outbox·큐·읽음/해결 상태     |
| 실시간 없음          | API 저장 성공, 발행 대기, 전용 큐, Reverb, 채널 인증         |
| 외부 발송 불명       | 제공자 결과·메시지 ID·멱등 키 확인 후 재시도 판단            |
| 지갑 불일치          | 완료 Operation·Transaction·Entry·예약 잔액 대조              |
| 파일 오류            | DB 미디어 참조·디스크·실제 파일·서명·접근 정책               |
| 통계 차이            | 집계 시간·대상·삭제/상태·권한 기준 확인                      |

지갑은 `php artisan hospital-wallet:audit-integrity`로 무결성을 점검할 수 있습니다. 업무 데이터를 직접 고치는 명령이 아니라 진단이지만 연결 대상과 로그 생성 영향을 먼저 확인합니다.

## 백업과 복구

DB 백업, 미디어 파일, APP_KEY·필요한 비밀 설정은 함께 복구 가능한 조합이어야 합니다. 덤프가 존재한다는 사실만으로 백업 성공을 확정하지 않습니다. 크기·해시·완료 상태와 격리 복원 가능성을 확인합니다.

복원 시 쓰기를 중지하고 백업 시점 이후 변경, 큐의 이전 ID·멱등 키, 예약·발송 상태를 대조합니다. DB만 과거로 되돌린 뒤 이미 발송된 SMS·메일·환불을 다시 실행하면 중복 부작용이 생길 수 있습니다.

백업·내보낸 대화·개인정보 파일을 Git에 넣거나 공개 디스크에 두지 않습니다. 보존·파기 기간은 실제 운영 정책으로 확정해야 합니다.

## 특별 명령

| 명령군                                    | 주의점                                                                 |
| ----------------------------------------- | ---------------------------------------------------------------------- |
| category:split-domains                    | 로컬 전환용. 검증 모드도 임시 DB를 만들 수 있음. 단순 읽기 검사가 아님 |
| prepare 계정·카테고리 / 권한 bootstrap    | 스키마·기본권한 변경 가능. 범위와 현재 상태 확인                       |
| development:normalize-korean              | 합성 데이터 표시값 보정. apply 시 변경·백업 생성                       |
| media:privatize·generate variants·cleanup | 파일 이동·생성·삭제. dry-run 여부와 대상 확인                          |
| dispatch-pending·queue retry              | 실제 전달·재발송 가능                                                  |
| 챗봇 이용 이벤트 prune                    | 보관 기간을 지난 통계 원본 삭제                                        |

정확한 명령명·옵션은 [콘솔 명령](../../app/Console/Commands), [일정](../../routes/console.php), 관련 도메인 Command를 확인합니다. 명령 도움말을 확인하기 위해서도 애플리케이션 부팅의 환경 영향을 고려합니다.

카테고리 전환의 행 단위 JSON 백업은 전체 DB·DDL 백업을 대신하지 않습니다. MySQL DDL은 트랜잭션 롤백을 기대할 수 없으며 코드만 되돌려 독립 ID 전환을 복구하지 않습니다.

## 성능 점검

운영 데이터 크기·선택도·페이지·기간·권한을 기록하고 쿼리 수·실행 계획·응답 시간·메모리·큐 지연을 분리 측정합니다. 샘플 데이터와 개발 서버 최초 컴파일 결과를 운영 성능으로 일반화하지 않습니다.

[기존 성능 테스트](../../tests/Performance)는 격리 환경에서만 사용합니다. 인덱스 변경·대량 분석·큐 부하는 별도 승인이 필요합니다.
