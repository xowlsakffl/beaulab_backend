# 비동기와 외부 연동

## 큐의 역할

현재 Horizon 설정은 Redis 큐를 역할별로 구분합니다.

| 큐                  | 책임                       |
| ------------------- | -------------------------- |
| critical            | 중요 비동기 작업           |
| mail                | 메일                       |
| sms                 | SMS                        |
| chat                | 회원 채팅 실시간           |
| hospital-chatbot    | 병의원 챗봇 실시간·복구    |
| notifications       | 사용자 알림·푸시 관련 작업 |
| staff-notifications | 직원 인앱 알림             |
| default             | 일반 작업                  |
| maintenance         | 파일·집계 등 유지보수      |

큐 이름과 실제 Job의 connection·queue를 함께 확인해야 합니다. 한 큐만 실행할 때 Horizon 전체를 시작하면 다른 발송 작업까지 처리할 수 있습니다.

## 저장과 전달의 분리

직원 알림·SMS·채팅은 업무 저장과 발행 상태를 구분하며 대기함·재시도 경로를 사용합니다. 동일한 작업을 재시도할 때 이벤트 키·멱등 키·처리 상태를 검사합니다.

`config/queue.php`의 연결 기본 `after_commit`은 false입니다. 모든 Job이 자동으로 커밋 뒤 실행된다고 믿지 말고 해당 Action의 afterCommit·발행 대기 구현을 확인합니다.

Redis 기본 `retry_after`는 360초이며 가장 긴 maintenance 작업자 timeout 300초보다 큽니다. 실제 환경변수로 덮어쓴 값도 이 관계를 유지해야 작업이 이중 실행될 위험을 줄일 수 있습니다.

## 실시간

Reverb는 전송 서버, 큐는 방송 작업자, API는 조회·쓰기와 채널 인가를 담당합니다. 셋 중 하나의 성공만으로 전체 송수신을 확인했다고 하지 않습니다.

직원·병의원은 같은 주체의 웹 세션·CSRF로 채널 인증을 합니다. 상담 메시지 변경은 식별자·무효화 알림을 받고 API에서 다시 읽는 계약을 우선합니다. 권한 회수 후에도 민감 본문이 계속 방송되지 않도록 채널과 payload를 함께 검토합니다.

네트워크 복귀, 구독 실패, 메시지 순번 누락은 클라이언트 재조회로 복구합니다. 병의원 온라인 표시는 상담창 열림이 아니라 활성 병의원 탭의 presence 기준입니다.

## 외부 호출

메일, SMS, 모바일 푸시, 저장소, 소셜 인증 등의 설정이 존재합니다. 실제 사용 제공자·키·웹훅·제한은 운영 설정에서 확인해야 합니다. 설치된 라이브러리를 실제 사용 중인 제공자로 단정하지 않습니다.

- 로컬 기본 검증은 `MAIL_MAILER=array` 또는 승인된 로컬 수신함, SMS·PUSH 비활성화를 사용합니다.
- 외부 호출 타임아웃·재시도는 제공자 어댑터별로 확인합니다. 응답 유실이 곧 미발송이라는 뜻은 아닙니다.
- 재전송 전에 제공자 메시지 ID·저장 상태·원래 멱등 키를 대조합니다.
- 서명된 URL과 토큰·전화번호·본문을 큐 로그에 그대로 출력하지 않습니다.

## 운영 확인

### SMS의 현재 제공 범위

[SmsServiceProvider](../../app/Providers/SmsServiceProvider.php)는 disabled와 local/testing의 log 제공자만 연결합니다. **실제 SMS 업체 연동은 현재 구현되어 있지 않습니다.** log 성공은 휴대폰 수신 성공이 아닙니다.

Batch와 수신자별 Delivery에 최종 본문·수신자 스냅샷을 저장하고 멱등 키와 request_hash를 비교합니다. API 성공은 발송 대기 등록이며 연락처 누락·제외·전송 실패와 다릅니다. 과거 휴대폰 인증·재설정 목적은 비활성 처리합니다. 현재 계정 인증은 이메일 흐름이며, 남아 있는 SMS 관계를 근거로 휴대폰 인증을 다시 사용하지 않습니다.

전송 결과가 불분명한 PROCESSING 복구는 제공자의 supportsIdempotentRetries가 보장하는 경우에만 재시도합니다. 현재 시도 상한은 SendSmsDeliveryAction의 5회이며, 실제 제공자 도입 시 인코딩·길이·재시도·접수 조회 계약을 다시 확인해야 합니다.

### 사용자 푸시

알림함과 채널별 Delivery, 기기, 수신 설정을 분리합니다. Delivery의 generation·lease_token·device_results가 오래된 작업자의 결과와 기기별 부분 성공을 구분합니다. 일부 기기 성공으로 SENT가 될 수 있으므로 전체 기기 도착 여부는 개별 결과를 봅니다. 제공자 수락 직후 장애에는 중복 가능성이 남아 있습니다.

기기 토큰의 현재 소유자·활성 상태와 마케팅 동의를 확인합니다. 공급자 호출 수와 사용자 수신함 항목 수는 같은 지표가 아닙니다.

### 운영 관찰

발행 대기 수, 가장 오래된 대기 시각, 실패 Job, 큐 지연, Reverb 연결과 실제 양방향 반영을 나눠 확인합니다. 광범위한 queue retry나 Redis flush는 복구의 기본 절차가 아닙니다.

[Horizon](../../config/horizon.php), [큐 연결](../../config/queue.php), [콘솔 일정](../../routes/console.php), [운영 절차](../operations/runbook.md)를 함께 봅니다.
